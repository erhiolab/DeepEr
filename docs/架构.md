# 架构

> DeepEr 整体架构说明. 以模块为单位, 一个模块一张运行线路图(mermaid), 供后续 Agent 汇总与扩展参考. 
>
> 关键约定: **LLM / TTS 采用"前端适配器 = 平台选择薄层, 后端适配器 = 协议实现"**, 协议构造 / 鉴权 / 请求 / 响应解析全部下沉到后端, 后端自数据库读取配置并解密, apiKey 不往返前端.

## 1. Tauri 命令注册

`src-tauri/src/lib.rs` 的 `invoke_handler` 是前端唯一可调用后端命令的入口表. `commands/` 下按业务域拆分子模块, 其中 `llm/` 与 `tts/` 为适配器实现层. 

```mermaid
flowchart TD
    FE["前端 invoke(cmd)"] -->|generate_handler 登记表| H["lib.rs invoke_handler"]
    H --> LLM
    H --> TTS
    H --> RSC["commands::resource / config / secret / live2d / ..."]
    subgraph LLM["commands/llm/ (每平台一命令)"]
        O["openai_responses.rs"]
        A["anthropic_messages.rs"]
        G["google_genai.rs"]
    end
    subgraph TTS["commands/tts/"]
        GT["gptsovits.rs"]
        TUTIL["通用: list_audio_files / read_audio_file"]
    end
```

- 命令名与 Rust 函数一一对应. 带结构体参数的命令, 前端需以**参数名作为一级 key**(如 `args: { ... }`), 而非平铺字段__否则报 `missing required key`. 
- 管理器参数(`AppHandle`/`State<Db>`)由 Tauri 自动注入, 前端无需传.

## 2. LLM 适配器运行线路

前端 `services/llm/adapters.ts` 持有 3 个平台适配器实例; `useLLMStore` 是统一入口. 适配器只做: 平台配置读写(UI 展示)/按平台调用对应后端命令/把后端错误码翻译为 i18n 文案. 协议构造全部在**后端**. 

```mermaid
sequenceDiagram
    participant UI as LLM 配置面板/对话
    participant Adapter as 前端适配器 (openai/anthropic/google)
    participant HTTP as services/llm/http.ts (桥接层)
    participant CMD as 后端 commands/llm/*.rs
    participant DB as SQLite config 表
    participant Platform as LLM 平台 API

    UI->>Adapter: synthesize/generate(req) 或 testConnection
    Adapter->>Adapter: loadConfig()(校验 apiKey/model → 无码直接返回翻译文案)
    Adapter->>HTTP: backendGenerate / backendTestConnection / backendListModels
    HTTP->>CMD: invoke(platform 命令, args)
    CMD->>DB: 自读 baseUrl / apiKey / model
    CMD->>CMD: decrypt apiKey(读 secret.key)
    CMD->>Platform: HTTP POST/GET(带 20s 超时)
    Platform-->>CMD: 响应
    CMD-->>HTTP: outcome{ ok, text/tokens, error, errorCode }
    HTTP-->>Adapter: 用 errorCode + i18n 翻译 error
    Adapter-->>UI: LLMGenerateResult / LLMTestResult
```

**错误码机制(后端→前端 i18n)**: 后端失败时返回 `errorCode`(如 `missing_api_key`/`missing_model`/`network_error`/`http_error`), 前端 `http.ts` 查到对应 i18n key 翻译; `http_error` 额外带 `status` 插值.

## 3. TTS 适配器运行线路

与 LLM 同构. 前端 `services/tts/gptsovits.ts` 只负责配置读写与调用后端命令; 后端 `commands/tts/gptsovits.rs` 自读配置(含 emotions 参考音频列表)并请求 GPT-SoVITS 本地服务, 产物保存在 `temp/tts/` 供前端经 asset 协议播放. 

```mermaid
sequenceDiagram
    participant UI as TTS 配置/合成面板
    participant Adapter as 前端 gptsovits 适配器
    participant CMD as 后端 commands/tts/gptsovits.rs
    participant DB as SQLite config 表
    participant TTS as GPT-SoVITS 本地服务

    UI->>Adapter: synthesize({text, voice?}) / testConnection
    Adapter->>Adapter: loadConfig()(emotions 为空→直接返回)
    Adapter->>CMD: invoke(tts_gptsovits_synthesize, {args:{...}})
    CMD->>DB: 自读 baseUrl / 采样参数 / emotions
    CMD->>CMD: 按 voice 找参考音频, 构造 GPT-SoVITS JSON
    CMD->>TTS: POST {base}/tts(60s 超时)
    TTS-->>CMD: 音频字节流
    CMD->>CMD: 保存到 temp/tts/tts_*.wav(附 prune 清理)
    CMD-->>Adapter: outcome{ ok, assetPath, error, errorCode }
    Adapter-->>UI: TtsSynthesizeResult(error 已 i18n 翻译)
```

- 通用工具 `tts_list_audio_files` / `tts_read_audio_file` 由前端直接调用做参考音频扫描/预览, 与平台无关. 
- TTS 错误码: `empty_text`/`missing_voice`/`network_error`/`http_error`/`empty_audio`.

## 4. 配置与密钥存储链路

所有配置统一存 SQLite `deeper.db` 的 `config` 表(key-value JSON). API Key 使用 AES-256-GCM 加密, 主密钥在应用数据目录 `secret.key` 中. 

```mermaid
flowchart TD
    UI["前端配置表单"] -->|invoke config.set/get| CC["commands/config.rs (get/set/delete)"]
    UI -->|invoke secret_encrypt/decrypt| SC["commands/secret.rs"]
    CC --> DB[("SQLite config 表")]
    SC --> KEY["secret.key (主密钥)"]
    ADAPT["后端适配器命令 (llm/tts)"] -->|直接读 config::get| DB
    ADAPT -->|secret::decrypt_str| KEY
```

- 配置读写命令由前端调用(UI 需要展示); 但**请求执行时**后端命令直接从 DB 读密文并解密, apiKey 明文不往返前端. 
- 配置键前缀与前端 `services/llm/*.ts`/`services/tts/gptsovits.ts` 中的 `PREFIX` 保持一致(如 `llm_openai_responses_*`/`tts_gpt_sovits_*`). 

#### 上下文 (contexts 表) 与 AI 链路

- `contexts` 表是对话/人设上下文的唯一事实源, 记录类型: `person` (当前人设, system 消息) / `talk` (对话) / `touch` (触摸) / `tts` (合成记录). 设为人设 (`persona_select`) 时后端自动写入 type=person 记录, 切换/清除时替换.
- 每条记录可带 `token_count` (估算) 与真实 `input_tokens` / `output_tokens` (LLM 返回), AI 回复记录还带 `hit_rate` (上下文命中率 = 本次请求实际使用的上下文 token / 库中上下文 token).
- 前端 `services/store/conversation.ts` 是 AI 统一入口: 构建上下文 → LLM 流式生成 → 记录真实 token 与命中率 → TTS 朗读 (`useTTSStore().speak` 统一处理 md 清洗 / AI 调参 / 记录). 已移除 Markdown 分词器, 流式直接整段渲染; 后续 MCP / 技能 / 工具扩展 `buildTalkMessages` 的上下文类型即可.

#### 适配器配置读写收敛

`services/llm/platform.ts` 提供平台公共配置工具(`loadPlatformBase`/`savePlatformBase`/`hasPlatformApiKey`/`clearPlatformApiKey`/`normalizeBaseUrl`/`validatePlatformConfig`), 三个 LLM 适配器只保留各自的扩展字段(如 OpenAI 的 `reasoningEffort`); 桥接层 `services/llm/http.ts` 按适配器的 `platform` 字段查命令表, 适配器与 store 不再各自维护命令名映射.

## 6. i18n 国际化

界面文案全部走 `vue-i18n`; 服务层与后端返回**错误码**, 由前端在收到后翻译, 后端不返回界面文案(避免双语耦合). 

```mermaid
flowchart LR
    BACK["后端错误码 (errorCode)"] --> BRIDGE["前端桥接层 http.ts / gptsovits.ts"]
    BRIDGE --> I18N["vue-i18n i18n.global.t(错误 key)"]
    LOC["services/i18n/locales/zh-CN.ts (errors.*)"] --> I18N
    I18N --> COMP["Vue 组件 useLanguages()"]
    COMP --> UI["界面文案"]
```

- 新增译文: `common.*` / `components.main.llm.*` / `components.main.tts.*` / `errors.*`. 
- `en-US.ts` 目前为空, 未配置的 locale 会 fallback 到 `zh-CN`. 
- 通用文案(保存/取消/删除/加载中/连接状态/保存并离开等)收敛到 `common.*` 公共组; 组件用 `useLangGroups({...})` 一次引用多个语言组(见 `services/i18n/useLanguages.ts`). 语言快照按 locale 记忆化.

## 7. 工具注册机与 Agent 循环

工具注册机是 Agent 的能力清单, 工具存放在独立 `tools` 表(SQLite), 字段:
`name`(英文调用名) / `label`(中文标题) / `description` / `provider`(internal/http/mcp/plugin) /
`executor`(provider 内执行目标) / `input_schema`(JSON Schema) / `config` / `enabled` / `builtin` / `version`.
执行与 Agent 循环全部在 Rust 侧 (`src-tauri/src/tool/` + `src-tauri/src/agent/`),
前端只做渲染与 `invoke("agent_run")` 总线; 当前只初始化内置工具, 注册写入命令留给后续插件系统.
工具多时不需要全量注入上下文, Agent 只需知道检索类工具即可按需查询:

| 工具名 | 作用 |
| --- | --- |
| `tool-search` | 按关键词搜索工具, 返回调用名 + 中文标题 + 描述(描述含调用方式) |
| `tool-list-all` | 返回全部工具清单 |
| `time-now` | 获取当前日期 / 时间 / 星期 / 时区 |
| `time-today` | 今日日期 + 星期 + 是否周末 / 工作日 |
| `time-zone` | 系统时区 + UTC 偏移 |
| `calculator` | 安全计算数学表达式(支持 + - * / % ^ 与括号) |
| `data-json` | JSON 解析 / 路径查询 / 美化输出(action: parse / query / stringify) |
| `data-text` | 文本模板替换 / 分割 / 合并(action: template / split / merge) |

```mermaid
flowchart TD
    UI["工具页 ToolList.vue (搜索/展开)"] --> LIST["tool_list / tool_search<br/>→ tools 表 (Definition Registry)"]
    CHAT["sendMessage / sendTouch / startPersona"] -->|invoke agent_run (只传消息文本)| CTX["上下文构造 agent/context.rs<br/>人设 + 历史 + token 预算 + 命中率"]
    CTX --> LOOP["Agent 循环 (src-tauri/src/agent/run.rs)"]
    LOOP -->|注入工具协议 system 消息| LLM["后端 LLM 命令 (按 llm_adapter 路由)"]
    LLM -->|回复含 <tool_call>| PARSE["agent/parser.rs"]
    PARSE --> EXEC["ToolService (src-tauri/src/tool/service.rs)"]
    EXEC --> REG["查定义 + enabled + Schema 校验"]
    REG --> PROV["provider=internal → RuntimeRegistry"]
    PROV --> RT["ToolSearchHandler / ToolListAllHandler<br/>(src-tauri/src/tool/internal.rs)"]
    EXEC -->|以 <tool_result> 回填 + contexts 留痕| LOOP
    LOOP -->|agent-tool-call 事件 + 最终回答| CHAT
```

- 调用协议: LLM 在回复中独占一行输出 `<tool_call name="工具名" args='{"参数":"值"}'></tool_call>`,
  循环执行后以 `<tool_result name="…" ok="true|false">…</tool_result>` 回填, 最多 6 轮.
- 内置工具由后端在数据库初始化时幂等写入 `tools` 表, 主窗口/桌宠窗口/Agent 循环共享同一份数据.
- 分层: `tool/model` 定义 / `tool/repository` Definition Registry / `tool/handler` ToolHandler trait + RuntimeRegistry /
  `tool/internal` 内置实现 / `tool/service` ToolService 统一调度. 新增内置工具 = 实现 `ToolHandler` + 种子表登记 + 加进 `builtin_handlers`.
- Agent 循环: `agent/parser` 解析 / `agent/prompt` 协议提示词(内置清单来自 tools 表) / `agent/run` 多轮编排;
  上下文构造 (`agent/context`) 也在后端: 用户消息由后端写入 contexts 表, 人设 + 历史按 token 预算裁剪并计算命中率;
  每轮工具调用以 `type=tool` 写入 contexts 表 (assistant=调用文本带本轮真实 usage, user=结果), 最终回答带累计真实 token 与命中率.
  前端 `services/agent/run.ts` 只做 invoke + 监听 `agent-tool-call` 事件展示执行过程.
- 后续插件系统可把 RuntimeRegistry 升级为 `inventory` 自动注册, 并新增 http/mcp Provider (实现 `provider` 字段分派即可).

## 8. 定时任务

定时任务像闹钟一样: 到点自动把任务内容通过消息队列发给 AI (不打断正在进行的回复).
调度在 Rust 后台线程持续运行, 不依赖窗口是否可见.

```mermaid
flowchart LR
    UI["定时任务页 Scheduled.vue"] -->|task_list/create/update/delete| TASK["commands/tasks.rs"]
    TASK --> DB[("tasks 表: title/content/kind/schedule JSON/enabled")]
    SCHED["调度线程 task/scheduler.rs (每秒检查)"] --> DB
    SCHED -->|到点 emit scheduled-task-due| STORE["services/store/schedule.ts"]
    STORE -->|⏰ 提示 + sendMessage| CONV["对话消息队列 conversation.ts"]
    CONV -->|agent_run| AI["Rust Agent 循环"]
```

- 时间设定 (schedule JSON 数组, 一个任务可多个): `once`(一次性, Unix 秒) / `hourly`(每小时的分钟) /
  `daily`(每天 HH:MM) / `weekly`(每周若干天 HH:MM).
- 任务类型: `permanent`(永久, 按循环重复) / `once`(一次性, 触发后自动删除).
- 循环防重: 调度线程维护内存 `last_fired` 表, 启动时按启动时刻起算, 错过的时间不补发;
  同一会话内新建/修改/启用任务会重置起点, 避免触发"过去的"时间.
- 「下一个任务」由 `task_next` 按当前时间计算, 前端每 30 秒轮询刷新.
- 到点触发走中间状态: 聊天里显示在中间(不占用户气泡), contexts 表以独立 `type=schedule` 记录,
  上下文构建时按用户输入一并给 AI, 与 talk/touch 区分开.
- Agent 可直接管理定时任务: 内置工具 `schedule-create-once`(一次性, 扁平 at 参数)/
  `schedule-create-recurring`(循环, 扁平 cycle/minute/times/weekdays 参数)/
  `schedule-update` / `schedule-list` / `schedule-delete`(分类「定时」), 走 ToolService 调用 tasks 表.
  内置工具种子移除旧工具时会自动清理已下架的 builtin 行.
