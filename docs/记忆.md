# 记忆设计

## 1. 核心理念

AI 的记忆系统分为多个层次: 

- **Context(上下文)**: AI 当前正在使用的短期 / 工作记忆
- **Summary(总结)**: 对较早 Context 进行压缩后的记忆
- **Memory(长期记忆)**: 从对话中提取的重要信息
- **Conversation Archive(历史记录)**: 完整保存所有原始对话

核心原则: 

> AI 不需要永远把所有历史都放进 Context, 而是通过"保存/压缩/遗忘/Recall"来管理记忆. 

---

# 2. Context: 短期 / 工作记忆

Context 是 AI 当前实际接收到的对话上下文. 

Context 具有: 

- 最近内容优先
- Token 数量限制
- 随着对话进行, 旧内容逐渐退出当前 Context
- 退出 Context 不代表原始数据被删除
- 重要内容可以通过 Summary 或 Memory 再次被 Recall

因此: 

```text
数据库中存在
≠
AI 当前记得
```

---

# 3. 原始 Context 永久保存

所有原始对话保存到 SQLite 的 `contexts` 表. 

```sql
CREATE TABLE contexts (
    id INTEGER PRIMARY KEY AUTOINCREMENT,

    conversation_id INTEGER NOT NULL,

    role TEXT NOT NULL,
    content TEXT NOT NULL,

    token_count INTEGER NOT NULL,

    created_at INTEGER NOT NULL
);
```

每一条 Context 都记录自己的 Token 数量. 

例如: 

```text
id    role        token_count    content

1     user        18             我想设计一个 AI 记忆系统
2     assistant   35             可以把 Context 当作短期记忆
3     user        12             我打算使用 SQLite
4     assistant   42             SQLite 很适合
...
```

`token_count` 在消息写入数据库时计算并保存. 

这样以后构建 Context 时, 不需要每次重新计算 Token. 

---

# 4. Context 不按照固定消息数量获取

不使用: 

```text
最近 100 条
```

作为主要规则. 

而是使用: 

> **Token Budget**

系统可以按照最大 Context 容量的百分比决定获取多少原始 Context. 

例如: 

```text
最大 Context = 1,000,000 Tokens
```

如果当前配置: 

```text
Raw Context Ratio = 20%
```

那么: 

```text
1,000,000 × 20%
= 200,000 Tokens
```

本次最多获取约: 

```text
200,000 Tokens
```

的原始 Context. 

---

# 5. 按 Token 从最新消息向前获取

例如: 

```text
Context Limit = 1,000,000 Tokens

Raw Context Ratio = 20%

Raw Context Budget = 200,000 Tokens
```

从最新 Context 开始: 

```text
#1000
#999
#998
#997
...
```

不断向前读取, 并累加 `token_count`: 

```text
#1000    1,200 tokens
#999     2,100 tokens
#998       800 tokens
...
```

直到: 

```text
累计 Token ≈ 200,000
```

然后停止. 

因此: 

```text
越新的 Context
    ↓
越优先保留
```

而不是简单按照消息数量截断. 

---

# 6. Context Budget 可以配置

建议把比例做成配置, 而不是写死. 

例如: 

```text
最大 Context: 
1,000,000 Tokens

System: 
5%

Memory: 
5%

Summary: 
15%

Raw Context: 
20%

Tool: 
10%

AI Output: 
45%
```

这里只是示例, 实际比例可以根据模型和应用进行调整. 

核心思想是: 

```text
1M Tokens
│
├── System
├── Memory
├── Summary
├── Raw Context
├── Tool Results
└── Output
```

其中 Raw Context 根据百分比决定最多读取多少原始消息. 

---

# 7. Summary: 上下文压缩

当原始 Context 越来越多时, 不直接删除旧 Context. 

使用 AI 对旧 Context 进行总结: 

```text
Context #1 ~ #50
        ↓
AI Summary
```

例如: 

```text
用户正在设计一个 AI Memory System. 
目前倾向使用 SQLite 保存完整对话, 
并将 Context 作为 AI 的短期工作记忆. 
```

原始内容可能有几千 Token. 

Summary 可能只有几百 Token. 

---

# 8. Summary 表

Summary 保存自己对应的原始 Context 范围. 

```sql
CREATE TABLE summaries (
    id INTEGER PRIMARY KEY AUTOINCREMENT,

    conversation_id INTEGER NOT NULL,

    start_context_id INTEGER NOT NULL,
    end_context_id INTEGER NOT NULL,

    level INTEGER NOT NULL DEFAULT 1,

    content TEXT NOT NULL,

    token_count INTEGER NOT NULL,

    status TEXT NOT NULL DEFAULT 'active',

    created_at INTEGER NOT NULL,

    FOREIGN KEY (start_context_id) REFERENCES contexts(id),
    FOREIGN KEY (end_context_id) REFERENCES contexts(id)
);
```

其中: 

- `start_context_id`: 总结覆盖的第一个原始 Context
- `end_context_id`: 总结覆盖的最后一个原始 Context
- `level`: Summary 层级
- `content`: AI 生成的总结
- `token_count`: Summary 自身的 Token 数量
- `status`: Summary 是否仍然有效

例如: 

```text
Summary #1

conversation_id = 1
start_context_id = 1
end_context_id = 50
level = 1

content =
用户开始设计 AI 记忆系统, 
决定使用 SQLite 保存对话, 
并将 Context 作为短期记忆. 
```

这样 Summary 永远可以追溯到: 

```text
contexts #1 ~ #50
```

---

# 9. 分层 Summary

Summary 可以继续被 Summary. 

例如: 

```text
原始 Context

#1 ~ #50
    ↓
Summary A

#51 ~ #100
    ↓
Summary B

#101 ~ #150
    ↓
Summary C
```

然后: 

```text
Summary A
Summary B
Summary C
    ↓
Level 2 Summary
```

形成: 

```text
                    Level 2 Summary
                          │
             ┌────────────┼────────────┐
             ▼            ▼            ▼
          Summary A    Summary B    Summary C
           Level 1      Level 1      Level 1
           #1~50        #51~100      #101~150
             │            │            │
             ▼            ▼            ▼
          原始 Context 原始 Context 原始 Context
```

原则: 

> 越久远的内容, 压缩程度越高; 越接近当前对话的内容, 保留的细节越多. 

---

# 10. Summary 的范围

同一个 `level` 最好不要出现重叠范围. 

例如: 

```text
Level 1:

#1   ~ #50
#51  ~ #100
#101 ~ #150
```

Level 2: 

```text
#1   ~ #150
#151 ~ #300
```

这样 Context Builder 可以根据距离选择不同层级的 Summary. 

---

# 11. Summary 不是删除原始 Context

Summary 只是原始 Context 的压缩表示. 

原始内容仍然存在: 

```text
contexts
    ↓
完整历史

summaries
    ↓
压缩历史
```

Summary: 

```text
start_context_id
end_context_id
```

可以直接追溯回: 

```text
contexts
```

如果 AI 对 Summary 有疑问, 可以重新读取对应的原始 Context. 

---

# 12. 渐进式遗忘

记忆不是简单的: 

```text
记住 / 删除
```

而是: 

```text
原始内容
    ↓
详细记忆
    ↓
Summary
    ↓
更高层 Summary
    ↓
核心事实
    ↓
完全遗忘
```

例如: 

刚刚发生: 

```text
用户说: 

我现在倾向使用 SQLite, 
但以后如果性能不够可能换数据库. 
```

较近: 

```text
用户倾向使用 SQLite, 
未来可能根据性能需求更换数据库. 
```

很久以后: 

```text
项目目前倾向使用 SQLite. 
```

必须避免: 

```text
"可能使用"
```

被错误总结成: 

```text
"确定使用"
```

Summary 不应该凭空增加信息. 

---

# 13. Memory: 长期记忆

Memory 与 Context 不同. 

Context: 

> 最近发生了什么? 

Memory: 

> 什么事情值得长期记住? 

例如: 

```text
用户正在开发 Starfall
```

可能进入长期 Memory. 

而: 

```text
用户今天喝了一杯咖啡
```

通常不需要成为长期 Memory. 

---

# 14. Memory 数据结构

建议使用独立的 `memories` 表. 

```sql
CREATE TABLE memories (
    id INTEGER PRIMARY KEY AUTOINCREMENT,

    content TEXT NOT NULL,

    type TEXT NOT NULL,

    importance REAL NOT NULL DEFAULT 0.5,
    confidence REAL NOT NULL DEFAULT 1.0,

    created_at INTEGER NOT NULL,
    updated_at INTEGER NOT NULL,
    last_accessed_at INTEGER,

    access_count INTEGER NOT NULL DEFAULT 0,

    expires_at INTEGER,

    status TEXT NOT NULL DEFAULT 'active'
);
```

Memory 类型可以包括: 

```text
fact
preference
project
event
relationship
core
```

---

# 15. Importance: 重要性

Importance 表示: 

> 这条 Memory 本身有多重要. 

可以使用: 

```text
0.1 = 几乎不重要
0.3 = 低重要性
0.5 = 普通
0.7 = 重要
0.9 = 非常重要
1.0 = 核心 / 永久记忆
```

例如: 

```text
用户今天吃了披萨
importance = 0.1

用户正在开发 Starfall
importance = 0.9

用户明确要求永久保存的信息
importance = 1.0
```

---

# 16. Importance 与 Relevance 分离

不要把 Importance 直接作为最终 Recall 权重. 

因为: 

> 一条记忆很重要, 不代表它与当前问题相关. 

例如: 

```text
用户名字
importance = 0.9
```

用户正在问: 

```text
Python 怎么排序? 
```

用户名字与这个问题没有关系. 

因此需要区分: 

```text
importance
    ↓
记忆本身的重要程度

relevance
    ↓
记忆与当前问题的相关程度

recency
    ↓
最近是否被使用

confidence
    ↓
这条信息是否确定

access_count
    ↓
过去被使用多少次
```

---

# 17. Recall: 记忆回忆

AI 每次收到新问题时, 可以主动搜索长期 Memory. 

例如: 

```text
用户: 

Starfall 的探索玩法应该怎么设计? 
```

系统搜索 Memory: 

```text
Starfall 是太空 RPG
Starfall 强调探索玩法
Starfall 有飞船系统
用户喜欢简洁回答
用户昨天吃了披萨
```

系统根据当前问题计算相关性. 

然后选择 Top K Memory. 

---

# 18. Recall Score

可以设计一个动态的 Recall Score: 

```text
Recall Score =
    Semantic Relevance
  + Importance
  + Confidence
  + Recency
  + Reinforcement
```

具体权重可以配置. 

例如: 

```text
Recall Score =
    0.50 × semantic_similarity
  + 0.25 × importance
  + 0.10 × confidence
  + 0.10 × recency
  + 0.05 × reinforcement
```

最终: 

```text
Score 高
    ↓
优先进入 Context

Score 低
    ↓
不加载
```

---

# 19. Memory Reinforcement

Memory 被再次使用时, 可以增强它. 

例如: 

```text
用户长期偏好简洁回答

access_count = 30
last_accessed_at = now
```

如果再次确认: 

```text
用户: 
以后回答简洁一点. 
```

可以: 

```text
confidence ↑
access_count ↑
last_accessed_at = now
```

经常被 Recall 的 Memory 会更加稳定. 

---

# 20. 永久 Memory

核心 / 永久 Memory 可以使用: 

```text
importance = 1.0
type = core
```

例如: 

```text
系统核心规则
用户明确要求永久保存的信息
非常稳定的重要事实
```

永久 Memory 应该谨慎产生. 

普通对话不应该轻易进入永久 Memory. 

---

# 21. Memory Tags

可以增加标签: 

```sql
CREATE TABLE memory_tags (
    memory_id INTEGER NOT NULL,
    tag TEXT NOT NULL
);
```

例如: 

```text
Memory:
Starfall 是一个太空 RPG. 

Tags:
starfall
game
space
rpg
project
```

标签可以帮助: 

- 分类
- 搜索
- 过滤 Recall
- 项目隔离
- 减少搜索范围

---

# 22. Embedding / Vector

Embedding 是把文字转换成一组数字. 

例如: 

```text
用户喜欢科幻游戏
```

经过 Embedding 模型: 

```text
[0.12, -0.38, 0.71, 0.04, ...]
```

这组数字就是: 

```text
Vector / Embedding
```

语义相近的文字, 通常会有比较接近的向量. 

例如: 

```text
用户喜欢科幻游戏
用户喜欢太空题材游戏
用户喜欢宇宙 RPG
```

即使关键词不完全一样, 也可以通过向量搜索找到相关 Memory. 

---

# 23. Vector Model

Vector / Embedding Model 与聊天模型不同. 

聊天模型: 

```text
输入
 ↓
理解 / 推理
 ↓
生成文字
```

Embedding 模型: 

```text
输入
 ↓
理解语义
 ↓
生成数字向量
```

Embedding 主要用于: 

```text
Semantic Search
```

即语义搜索. 

---

# 24. Vector Database

普通 SQLite 擅长: 

```sql
WHERE type = 'project'
```

或者: 

```sql
WHERE content LIKE '%Starfall%'
```

Vector Database 擅长: 

> 找出与当前问题语义最接近的内容. 

例如: 

```text
用户: 

Starfall 的宇宙探索应该怎么做? 
```

可能找到: 

```text
Starfall 是太空 RPG
Starfall 强调探索玩法
Starfall 有飞船系统
```

即使原文没有完全相同的关键词. 

---

# 25. 第一阶段不需要 Vector Database

初期可以只使用: 

```text
SQLite
+
普通搜索
+
Tags
+
Importance
+
时间
```

等 Memory 数量增加以后, 再加入: 

```text
Embedding
+
Vector Search
```

甚至可以先把向量直接保存到 SQLite. 

不需要一开始就引入独立 Vector Database. 

---

# 26. Context Builder

整个记忆系统的核心组件是: 

```text
Context Builder
```

它负责决定: 

> 这一次到底应该给 AI 看什么? 

输入: 

```text
当前用户消息
```

然后分别获取: 

```text
最近原始 Context
        +
历史 Summary
        +
相关 Long-term Memory
        +
System Prompt
        +
Tool Results
```

最后按照 Token Budget 组合. 

---

# 27. Context Builder 的 Token 分配

假设模型支持: 

```text
1,000,000 Tokens
```

可以配置: 

```text
System       = 5%
Memory       = 5%
Summary      = 15%
Raw Context  = 20%
Tool         = 10%
Output       = 45%
```

得到: 

```text
1,000,000 Tokens
│
├── System       50,000
├── Memory       50,000
├── Summary     150,000
├── Raw Context 200,000
├── Tool        100,000
└── Output      450,000
```

这里的比例只是配置示例. 

真正使用时应该根据具体模型调整. 

---

# 28. Raw Context 获取机制

Raw Context 的获取流程: 

```text
读取配置: 

context_max_tokens = 1,000,000
raw_context_ratio = 0.20
```

计算: 

```text
raw_context_budget =
    context_max_tokens × raw_context_ratio

= 1,000,000 × 0.20

= 200,000 Tokens
```

然后: 

```text
从最新 Context 开始
        ↓
读取 token_count
        ↓
累加
        ↓
未超过 200,000
        ↓
继续读取上一条
        ↓
达到预算
        ↓
停止
```

因此不需要每次重新计算消息 Token. 

---

# 29. Summary 也有自己的 Token Budget

例如: 

```text
Summary Budget = 15%
```

那么: 

```text
1,000,000 × 15%
= 150,000 Tokens
```

Context Builder 可以根据历史距离选择 Summary: 

```text
最近历史
    ↓
Level 1 Summary

较远历史
    ↓
Level 2 Summary

非常远历史
    ↓
Level 3 Summary
```

最终 Summary 也不能超过自己的 Token Budget. 

---

# 30. Memory 也有自己的 Token Budget

例如: 

```text
Memory Budget = 5%
```

那么: 

```text
1,000,000 × 5%
= 50,000 Tokens
```

系统通过 Recall Score 排序: 

```text
Memory #23   Score 0.94
Memory #51   Score 0.91
Memory #12   Score 0.87
Memory #89   Score 0.71
...
```

从高到低加入 Context. 

直到: 

```text
Memory Token Budget
```

用完.

# 33. 三种信息的区别

| 类型 | 作用 | 是否永久保存 | AI 是否默认读取 |
|---|---|---|---|
| Context | 当前工作记忆 | 是 | 是 |
| Summary | 历史压缩 | 是 | 按需 |
| Memory | 长期重要信息 | 是 | 按相关性 |
| Archive | 完整历史 | 是 | 默认不读取 |

核心概念: 

```text
Context
= 我现在记得什么

Summary
= 我以前大概经历过什么

Memory
= 什么事情值得长期记住

Archive
= 我实际上经历过什么
```

---

# 34. 完整生命周期

```text
用户发送消息
      ↓
写入 contexts
      ↓
计算并保存 token_count
      ↓
进入当前 Raw Context
      ↓
Context 越来越长
      ↓
按照 1M Token Context 的百分比获取数据
      ↓
旧内容逐渐退出 Raw Context
      ↓
AI 对旧 Context 进行 Summary
      ↓
写入 summaries
      ↓
检查是否存在重要信息
      ↓
重要信息 → memories
普通信息 → 留在 archive
      ↓
未来用户提出相关问题
      ↓
Context Builder
      ↓
读取: 
    Raw Context
    Summary
    Memory
      ↓
Recall / Ranking
      ↓
按照各自 Token Budget 组合
      ↓
形成 Final Context
      ↓
发送给 AI
      ↓
AI "想起"过去的事情
```

---

# 35. 核心设计原则

### 原则 1: 原始数据不因为 Context 限制而丢失

```text
contexts = 完整历史
```

---

### 原则 2: 每条 Context 保存 Token 数

```text
token_count
```

Context Builder 可以直接根据 Token 数量计算预算. 

---

### 原则 3: Context 使用百分比控制

不要固定: 

```text
100 条
```

而使用: 

```text
Context 最大 Token 数
×
Raw Context 百分比
```

例如: 

```text
1M × 20%
=
200K Raw Context
```

---

### 原则 4: Summary 是压缩, 不是删除

```text
原始 Context
    ↓
Summary
```

原始内容依然可以通过: 

```text
start_context_id
end_context_id
```

追溯. 

---

### 原则 5: Memory 是主动提取的长期知识

不是所有历史都值得成为 Memory. 

---

### 原则 6: Importance 与 Relevance 分离

```text
Importance
= 这条记忆本身重要吗? 

Relevance
= 这条记忆现在有用吗? 
```

---

### 原则 7: Recall Weight 动态计算

当前问题不同: 

```text
Relevance 不同
Recency 不同
```

因此最终 Recall Score 动态计算. 

---

### 原则 8: 越远的内容越压缩

```text
最近
↓
原始消息

较近
↓
Level 1 Summary

较远
↓
Level 2 Summary

很远
↓
Level 3 Summary

重要
↓
Long-term Memory
```

---

# 36. 最终目标

整个 AI 的记忆系统不是: 

```text
无限 Context
```

而是: 

```text
无限历史
+
有限工作记忆
+
Token Budget
+
分层压缩
+
长期记忆
+
智能 Recall
```

最终实现: 

```text
刚刚发生的事
→ 记得原话

最近发生的事
→ 记得详细过程

很久以前的事
→ 记得摘要

重要的事
→ 长期记住

不重要的事
→ 慢慢淡出

用户再次提起
→ 从 Summary / Memory / Archive 中重新想起
```

核心思想: 

> **不是让 AI 永远记住一切, 而是让 AI 拥有"记住/压缩/遗忘/想起"的能力. **

> **Context 是 AI 当前的意识, Summary 是压缩后的过去, Memory 是值得长期保留的知识, 而 SQLite 保存的是完整经历. **
